## 1. Функциональные требования

1. Система должна показывать индикатор загрузки при ожидании каталога, чтобы пользователь видел выполнение запроса. US01 / FR01.
2. Система должна отображать карточки с названием, типом, калориями, числом блюд и ценой за день при успешной загрузке валидного каталога, чтобы пользователь сравнил рационы. US01 / FR02.
3. Система должна отбирать карточки по типу при выборе фильтра, чтобы пользователь видел подходящие наборы. US01 / FR03.
4. Система должна показывать пустое состояние со сбросом фильтра при отсутствии совпадений, чтобы пользователь вернулся ко всем рационам. US01 / FR04.
5. Система должна показывать пустое состояние каталога при пустом ответе API, чтобы пользователь понимал отсутствие доступных рационов. US01 / FR04.
6. Система должна показывать сообщение сбоя каталога при неудачном запросе, чтобы пользователь понимал причину отсутствия карточек. US07 / FR05.
7. Система должна повторять запрос каталога при нажатии «Повторить загрузку», чтобы пользователь восстановил отображение без reload. US07 / FR05.
8. Система должна открывать диалог с блюдами, БЖУ, ингредиентами и аллергенами при нажатии «Смотреть меню», чтобы пользователь изучил фиксированный рацион. US02 / FR06.
9. Система должна закрывать диалог при Escape или нажатии закрытия, чтобы пользователь вернулся к каталогу. US02 / FR07.
10. Система должна добавлять единицу рациона в корзину при нажатии «Добавить», чтобы пользователь сформировал заказ. US03 / FR08.
11. Система должна изменять количество позиции в диапазоне 0–9 при нажатии +/−, чтобы пользователь скорректировал число наборов; значение ноль удаляет позицию. US03 / FR09.
12. Система должна удалять позицию при нажатии «Удалить», чтобы пользователь отказался от выбранного набора. US03 / FR09.
13. Система должна изменять период всего заказа на 1 или 7 дней при выборе переключателя, чтобы заказ соответствовал планируемому сроку. US04 / FR10.
14. Система должна пересчитывать итог по формуле Σ(цена × количество) × days + 15000 копеек при изменении корзины или периода, чтобы пользователь видел окончательную стоимость; пустая корзина имеет итог ноль. US03, US04 / FR11.
15. Система должна блокировать кнопку оформления при пустой корзине, чтобы не создавать пустой заказ. US03 / FR12.
16. Система должна показывать приглашение выбрать рацион при открытии оформления с пустой корзиной, чтобы пользователь вернулся к каталогу. US03 / FR12.
17. Система должна устанавливать min даты равным today+2 календарных дня при открытии формы, чтобы пользователь видел минимальный срок производства. US05 / FR13.
18. Система должна отклонять отправку с ошибкой при пустой, ранней или невалидной дате, чтобы пользователь исправил ввод без потери заказа. US05 / FR14.
19. Система должна сохранять выбранный интервал 09:00–13:00 или 14:00–18:00 при изменении поля, чтобы время первой доставки было однозначным. US05 / FR15.
20. Система должна отклонять отправку с ошибкой при отсутствии согласия с демонстрационным режимом, чтобы пользователь понимал отсутствие реальной оплаты. US06 / FR16.
21. Система должна блокировать повторную отправку при выполняющемся Mock-запросе, чтобы создать только одно подтверждение. US06 / FR17.
22. Система должна показывать номер, дату, интервал, период, итог и пояснение демонстрационного режима при успешном Mock-ответе, чтобы пользователь проверил результат. US06 / FR18.
23. Система должна очищать корзину при успешном оформлении демозаказа, чтобы не повторить уже подтверждённый выбор. US06 / FR18.
24. Система должна показывать ошибку без очистки корзины и формы при сбое оформления, чтобы пользователь повторил запрос. US07 / FR19.
25. Система должна показывать гостевое сообщение с возвратом при открытии кабинета или ответе 401, чтобы пользователь понимал границы демоверсии. US08 / FR20.

## 2. Нефункциональные требования

1. Каталог не должен иметь горизонтальной прокрутки при ширине 320, 375, 768 и 1440 CSS px; проверка scrollWidth ≤ innerWidth.
2. Диалог меню должен иметь доступное имя, закрываться Escape и возвращать фокус к кнопке открытия; проверка DOM и клавиатурой.
3. Суммы должны рассчитываться целыми безопасными копейками с точным совпадением ожидаемых значений; дробные, логические и отрицательные цены отклоняются.
4. Изменение количества и периода должно пересчитывать итог локально без дополнительного запроса API; проверка component test.
5. Каждое поле оформления должно иметь label, ошибка должна иметь role=alert; проверка доступных ролей.
6. На одно оформление во время loading должно приходиться не более одного Mock-вызова; проверка двух нажатий.
7. Видимые интерактивные цели на узком экране должны иметь размер не менее 44×44 CSS px и видимый focus; проверка CSS и DOM.
8. Основные пары цветов обычного текста должны иметь контраст не менее 4.5:1, крупного текста — не менее 3:1; проверка расчётом относительной яркости.
9. Суммарный JS+CSS production-сборки должен быть не более 350000 байт gzip; проверка scripts/check-build.mjs.
10. Приложение должно содержать ноль внешних шрифтов, трекеров, секретов, персональных и платёжных полей; проверка исходников.
11. Невалидный каталог должен приводить к состоянию error без необработанного падения React; проверка адаптера и компонента.
