# Техническое задание FoodTech

## Описание проекта

Адаптивное веб-приложение выбора готового питания. Реализация ДЗ4 охватывает
каталог, меню рациона, корзину и демонстрационное оформление. Реальных
заказов, платежей, аккаунтов и backend нет. Система не принимает персональные
данные; все меню и цены учебные. ЦА — занятые взрослые 25–45 лет.

## Архитектура

React + Vite, JavaScript ES modules, UI-библиотека Pico CSS с собственным
слоем визуальных стилей. Каталог загружается fetch из public/catalog.json.
API-адаптер отделён в src/data/api.js, доменные правила — src/domain/order.js,
компоненты — src/components. Роутинг через hash: /catalog, /checkout,
/success и /account. Сервер не нужен; прямое открытие hash работает на
статическом хостинге. Cart и days хранятся в памяти текущей вкладки;
после перезагрузки сбрасываются. История реальных заказов отсутствует.

## Функциональные требования

### Каталог и фильтры

FR01. Система должна отображать состояние загрузки при запросе каталога,
чтобы пользователь видел, что данные ещё поступают. История US01.

FR02. Система должна отображать карточки валидного каталога при успешной
загрузке, чтобы пользователь сравнил название, калории, число блюд и цену за день. US01.

FR03. Система должна фильтровать карточки по типу при выборе фильтра,
чтобы пользователь видел подходящие рационы. US01.

FR04. Система должна показывать сообщение и сброс фильтра при отсутствии
результатов, чтобы пользователь вернулся к полному каталогу. US01.

FR05. Система должна показывать ошибку и кнопку повтора при сбое каталога,
чтобы пользователь повторил запрос без перезагрузки страницы. US07.

### Меню рациона

FR06. Система должна открывать диалог с блюдами, БЖУ, составом и аллергенами
при выборе «Смотреть меню», чтобы пользователь изучил готовый рацион. US02.

FR07. Система должна закрывать диалог при Escape или нажатии «Закрыть меню»,
чтобы пользователь вернулся к каталогу. US02.

### Корзина и расчёт

FR08. Система должна добавлять единицу выбранного рациона при нажатии
«Добавить», чтобы пользователь сформировал заказ. US03.

FR09. Система должна изменять количество позиции при +/−, чтобы пользователь
скорректировал заказ; значение 0 удаляет позицию. Максимум 9 наборов на позицию. US03.

FR10. Система должна изменять длительность всего заказа на 1 или 7 дней
при выборе периода, чтобы стоимость соответствовала выбранной длительности. US04.

FR11. Система должна пересчитывать итог при изменении корзины или периода,
чтобы показать Σ(цена за день × количество) × days + 15000 копеек.
Доставка добавляется один раз; пустая корзина имеет итог 0. US03, US04.

FR12. Система должна блокировать оформление при пустой корзине,
чтобы не создавать пустое подтверждение. Прямая ссылка /checkout показывает
пустое состояние и возврат к каталогу. US03.

### Оформление и подтверждение

FR13. Система должна ограничивать первую дату значением today+2 календарных
дня при открытии формы, чтобы соблюсти минимальный срок производства. US05.

FR14. Система должна показывать ошибку при пустой, невалидной или ранней дате,
чтобы пользователь исправил ввод без потери корзины. US05.

FR15. Система должна принимать один из интервалов 09:00–13:00 и 14:00–18:00
при оформлении, чтобы выбор доставки был однозначен. Зона фиксирована:
«Москва — демонстрационная зона»; адрес не запрашивается. US05.

FR16. Система должна требовать подтверждение демонстрационного режима
при отправке, чтобы пользователь понимал отсутствие реального платежа. US06.

FR17. Система должна блокировать повторную отправку во время выполнения
Mock-запроса, чтобы создать только одно подтверждение. US06.

FR18. Система должна показывать номер, дату, интервал и итог при успешном
Mock-ответе, чтобы пользователь проверил результат. Корзина очищается. US06.

FR19. Система должна сохранять корзину и форму при сбое Mock API,
чтобы пользователь повторил отправку. US07.

FR20. Система должна показывать гостевое состояние при /account или
ответе 401, чтобы пользователь понимал, что личный кабинет недоступен
в учебной версии; корзина сохраняется, доступен возврат. US08.

| Корзина | Пересчёт после действия происходит без отдельного сетевого запроса | Component test, локальный state |

| Все экраны | Production JS+CSS суммарно не более 350 КБ gzip | Замер файлов dist после сборки |
| Все экраны | Нет внешних шрифтов, трекеров, секретов и обработки персональных данных | Проверка исходников/сетевых запросов |

сервера и SLA доставки не заявляются. Загрузка Mock-каталога зависит от хоста.

## Состояния и обработка ошибок

| Сценарий | Сообщение и действие | Сохранение данных |
|---|---|---|
| Каталог загружается | «Загружаем рационы…», role status | Корзина сохраняется |
| Сетевая ошибка/500 | «Не удалось загрузить меню», «Повторить загрузку» | Корзина сохраняется |
| Каталог пуст | «Пока нет доступных рационов» | Пустой заказ не оформляется |
| Фильтр без результатов | «Нет рационов по этому фильтру», «Все рационы» | Фильтр можно сбросить |
| Невалидная/ранняя дата | Ошибка у формы, отправка не выполняется | Дата и корзина сохраняются |
| Пустая корзина | Приглашение выбрать рацион, кнопка оформления недоступна | Ошибочного запроса нет |
| Mock-запрос оформления выполняется | «Подтверждаем…», кнопка disabled | Форма сохраняется |
| Сбой оформления | «Не удалось оформить демозаказ. Повторите попытку» | Корзина и дата сохраняются |
| Неавторизованный доступ | «Личный кабинет недоступен в демоверсии», возврат | Нет выдуманного успешного входа |
| Успех | «Демозаказ оформлен», явно «Оплата не списывалась» | Снимок подтверждения в памяти |

Для ручной проверки Mock-ошибок предусмотрены query-параметры:
`?demo=catalog-error`, `?demo=empty`, `?demo=submit-error`, `?demo=unauthorized`.
Они не представлены как реальные возможности платёжного провайдера.

## Данные и критерии сдачи

Рацион: id, name, type, calories, priceKopecks, meals, protein, fat,
carbs, ingredients, allergens, description. Цена за один день.
Корзина: список id и quantity. Количество 1–9. После уменьшения до 0 — удаление.

Приёмка: реализованы US01–US08; минимум 3 автоматических теста ключевых
компонентов проходят; есть позитивные и негативные проверки; адаптивность
подтверждена четырьмя viewport; код собирается; README содержит команды;
сохранены промпты, скриншоты и отчёт разработки. Исходники и документы — GitHub.
Подробные Gherkin-сценарии находятся в user_stories.md.

requirements.md (YAML, зависимости, ровно одна оптимизация и два раздела).
Happy Path с полями User goal / Actions / Touchpoints / Emotions /
