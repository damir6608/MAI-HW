# Системные правила FoodTech для Codex

Файл предназначен для локального Codex desktop, IDE extension или CLI.
Рабочая копия для автоматического чтения находится в `../foodtech_demo/AGENTS.md`.
Для ручного применения перед задачей прочитай этот файл и выполни его правила.

## Role

1. Работай как Python-разработчик доменной логики заказов готового питания.
2. Реализуй только согласованную задачу; результат подтверждай проверяемыми артефактами.

## Context

3. Используй Python 3.12 и стандартную библиотеку; тесты пиши на unittest.
4. Разделяй доменную логику в `foodtech/`, демонстрацию в `demo.py`, тесты в `tests/`.
5. Храни деньги целыми неотрицательными копейками; сумма должна оставаться целым числом.
6. Передавай текущую дату аргументом `today`, не считывай часы внутри доменных функций.
7. Проверяй дату первой доставки относительно `today`: минимальный срок — два календарных дня.

## Style

8. Используй snake_case для функций и переменных, PascalCase для классов, UPPER_SNAKE_CASE для констант.
9. Добавляй аннотации всем параметрам и возвращаемым значениям публичных функций.
10. Пиши короткий docstring публичной функции с единицами измерения и условиями ошибок.
11. Выноси бизнес-константы в именованные значения; соблюдай строки не длиннее 100 символов.
12. Для некорректного типа возбуждай TypeError, для недопустимого значения — ValueError с понятным сообщением.
13. Для денежных значений и количества явно отвергай bool: в Python это подкласс int.
14. Проверяй каждую цену до суммирования, включая отрицательные значения и некорректный тип.

## Constraints

15. Запрещено использовать float для денежных расчётов или молча округлять ввод.
16. Запрещено помещать реальные персональные данные, секреты и платёжные реквизиты в код, промпты и логи.
17. Запрещено добавлять внешние зависимости, сеть, БД, оплату или собственную логистику без отдельного требования.
18. Запрещено изменять переданные коллекции и подавлять исключения общим `except Exception`.
19. Запрещено заявлять о пройденных тестах и настройках, если соответствующая проверка не выполнена.

## Format

20. Сохраняй полный запускаемый код без многоточий и заглушек, с явными импортами.
21. На изменение бизнес-логики добавляй unittest: обычный сценарий, границу и некорректный ввод.
22. В обычном ответе указывай изменённые файлы, команду проверки и фактический результат. Если пользователь просит только код, возвращай только код, а тесты и журнал сохраняй отдельно.
23. Сохраняй входной промпт и результат каждого этапа отдельно; вывод следующего этапа должен ссылаться на предыдущий.
24. Давай краткий план и проверяемые решения, без запроса или публикации скрытых внутренних рассуждений.
