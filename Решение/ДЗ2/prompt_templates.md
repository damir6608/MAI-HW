# Библиотека промптов FoodTech

Замени значения `{{...}}` перед использованием. Для работы с кодом сначала
подключи `rules.md` либо открой проект с `AGENTS.md`. Каждый шаблон и пример
содержит Role, Task, Context, Format. Примеры — готовые тексты запросов;
выполненные запросы и реальные результаты отдельно сохранены в `chain/`.

## 1 Генерация функции

```markdown
### Role
Python-разработчик доменной логики FoodTech.
### Task
Реализуй {{функция}} по {{контракт}}.
### Context
Python 3.12, стандартная библиотека, rules.md. Вход: {{типы и примеры}}.
Бизнес-ограничения: {{границы}}. Целевой файл: {{путь}}.
### Format
Полный Python-файл, тесты обычного и граничного сценария, команда проверки.
```

Пример:

```markdown
### Role
Python-разработчик FoodTech.
### Task
Реализуй calculate_total(prices_kopecks, delivery_kopecks=0).
### Context
Python 3.12, rules.md, foodtech/pricing.py. Список целых цен в копейках;
доставка неотрицательна. [90000, 110000] и 15000 дают 215000.
Пустой список допустим; bool и float запрещены; ввод не изменять.
### Format
Полный код, unittest для суммы и неверного ввода, команда запуска.
```

## 2 Рефакторинг с сохранением поведения

```markdown

Не менять {{поведение, API, исключения}}.
### Format
Патч, краткое объяснение изменений и результаты существующих тестов.
```

Пример:

```markdown

Патч либо обоснованный отказ от лишнего изменения; фактический вывод unittest.
```


## 5 Декомпозиция сложной задачи

```markdown
минимум два календарных дня до доставки, без сети и оплаты.

Три этапа с входами и выходами; RTCF-промпт для каждого, критерии приёмки.
```


## 11 Перечень требований для AI реализации

```markdown
### Role
Тимлид и архитектор FoodTech.
### Task
Прочитай {{истории с Gherkin}}, выяви зависимости, сформируй требования,
предложи ровно одну оптимизацию и проверь сохранение исходной логики.
### Context
Не добавляй функций вне историй. Каждое ФТ описывает одну функцию и допускает
однозначный тест; НФТ измеримы. При противоречиях остановись и запроси уточнение.
Не используй «может», «желательно», «иногда».
### Format
Только итоговый Markdown. YAML frontmatter с техническими параметрами,
зависимостями и решением по оптимизации. Ровно два раздела:
«1. Функциональные требования» и «2. Нефункциональные требования».
Нумерация в каждом с 1. ФТ: «Система должна [действие] при [условие], чтобы [результат]».
```

Пример:

```markdown
### Role
Тимлид FoodTech.
### Task
Преобразуй истории этапов выбора набора и даты из предыдущего результата в требования.
### Context
Вставь полный список историй с Given/When/Then. Используй только их условия.
Если НФТ в них нет, прямо укажи отсутствие исходных НФТ, не придумывай SLA.
Предложи одну оптимизацию: единое правило минимальной даты доставки.
### Format
YAML frontmatter: project, stack, dependencies, optimization, validation.
Затем только два раздела ФТ и НФТ; атомарные ФТ по заданному шаблону,
нумерация с 1. Покажи в metadata, сохраняет ли оптимизация зависимости.
```

Шаблоны 9–11 адаптируют все три приложенных промпта к RTCF, сохраняя
их ограничения. Для требования ровно двух итоговых разделов зависимости
и единственная оптимизация размещаются в YAML, а не добавляют третий раздел.
